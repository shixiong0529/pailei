入口：正式 Web API `POST /api/scan`，两次均使用 `force=true`

## 结论

在同一台机器、同一服务配置、同一证券和相同本地 PDF 缓存条件下，完整报告生成时间从
**120.030 秒**降至 **61.383 秒**，减少 **58.647 秒（48.9%）**。

本次没有减少公告、PDF、财务数据、规则、证据或模型上下文。优化点仅为：将相互独立的
模型批次从串行等待改为最多 2 路并行；所有结果仍按原批次顺序合并。

## 实现与保护措施

- `LLM_PARALLEL_CALLS=2` 为默认值；供应商限制并发时可设为 `1` 恢复串行。
- 并发前按原批次顺序规划预算；预算不足时先运行可执行批次，按实际成本结算后再判断后续批次。
- 每个请求原子预留预算，防止两个并发请求同时越过单次扫描预算上限。
- 单批失败不取消其他已提交批次，有效结果继续保留并如实记录缺口。
- 并发完成后仍按输入批次顺序合并，避免响应先后改变报告顺序。
- SQLite 模型用量写入使用极短串行区，避免两个响应同时完成时争用写锁。

## 验证

- 原有确定性测试：58/58 通过。
- 验收回归与独立边界测试：89/89 通过。
- 并发专项断言：两批确实同时执行、结果顺序稳定、部分失败保留有效批次、低预算按原顺序放行。
- 优化后正式报告 HTTP 200，服务健康检查正常，在线报告可打开。

## 适用边界

61.383 秒是一次真实样本结果，不是所有股票的固定耗时。总耗时仍受公告接口、财务接口、PDF
复杂度和模型服务当时负载影响。该样本的公开数据请求累计耗时优化前约 23.15 秒、优化后约
25.90 秒，网络反而略慢，因此本轮总耗时下降主要来自模型批次并行，而非更有利的公开数据响应。

## V1.2 最终复验补充

最终修复后使用正式 Web API、`force=true`、完整公告/PDF/规则/证据/模型流程重新生成：

| 样本 | 交接样本 | 最终实测 | 缩短 | 最终 task_id |

腾讯连续两次强制生成分别为 30.7s 和 25.3s，第二次较第一次再缩短 17.6%。两份报告的
1,234 条财务事实、168 条公告、25 份 PDF、49/49 条已复核证据、52 项规则及最终 HTML 内容一致。

本轮新增一项不改变分析材料的缓存修复：长 PDF 按明确页段成功解析后，即使结果标记为
`truncated=true`，也写入以 SHA256、解析器版本、起始页和最大页数为键的缓存。此前这类成功结果
被误当作不完整失败，每次扫描都会重复解析。缓存采用同目录临时文件加原子替换，避免并发扫描
读取半写文件。

以贵州茅台 2025 年年报（143 页，解析前 120 页）做隔离基准：修复前连续两次分别为 4.486s、
4.398s，均未产生缓存；修复后首次为 4.775s，第二次命中缓存为 0.002s。输出页数、总页数和
截断标记一致，没有删页、降采样或减少证据。

最终三份报告均为 `report_version=1.2`，在线、下载与本地 HTML 逐字节一致。耗时仍会随公开数据源
和模型服务负载波动，上表用于说明本机本次真实运行结果，不承诺固定响应时间。

真实复验还发现事件抽取在 4,000 输出 token 上限时可能因思考 token 占满而截断。最终实现只把
事件抽取的输出上限提高到至少 8,000，其他模型步骤保持原配置；事件批次仍最多 2 路并行。最终
茅台和万科各 2 次事件调用均完整返回，模型截断缺口为 0，总耗时分别保持在 69.5s 和 69.4s。
